# ADR 0002：Provider 配置从环境变量迁到数据库与界面

- 状态：提议（待评审，未实现）
- 日期：2026-11-12
- 关联：`notes/provider-accounts.md`、`TODO.md` G2.1/G2.4、`docs/status.md`

## 背景

目前 provider 的“注册”分属两处：

- **适配器实现**在代码里：`ProviderName` 是封闭枚举，`ProviderRegistry` 在启动时由
  `build_providers()` 构建一次且不可变。
- **配置**在 `.env` 与部署行里：每个适配器一组 `*_API_KEY` 与默认 `base_url`；
  `model_deployments` 另可覆盖 `credential_env`（仅变量名）与 `base_url`。

结果是运维要改 provider 必须改环境变量并重启；同一个适配器想配多个账号（不同 key 或代理），
只能在每条部署上重复填写；界面上看不到“哪些 provider 已配置、凭证是否存在”。

同时，`AGENTS.md` §6 要求凭证只从环境变量或 secret manager 读取。直接把密钥搬进数据库会突破
这条边界，必须先有加密与轮换方案。

## 决策

1. **适配器是代码，配置是数据。** 不把适配器的导入路径或类名存进数据库，也不做运行时动态加载。
   界面只能启用和配置已经实现的适配器；新增协议仍需写代码。
2. **新增 `provider_accounts` 表**，作为“一个已配置上游”的唯一记录：`name`、`adapter`、
   `base_url`、`credential_env`（变量名）、`api_version`（Azure）、`enabled`、`version`。
   唯一约束为 `name` 与 `(adapter, base_url, credential_env)`。
3. **模型与部署通过可空 `account_id` 引用账号**，外键 `ON DELETE RESTRICT`；引用时
   `account.adapter` 必须等于模型/部署的 `provider`，否则 400。`provider` 列保留，因为它出现在
   `/v1/models` 与用量记录中。
4. **禁止混用。** 部署同时设置 `account_id` 与旧的 `credential_env`/`base_url` 时返回 400，
   避免两套配置并存导致优先级不可见。
5. **解析顺序固定**：部署账号 → 部署旧字段（弃用中）→ 模型账号（供 `synthetic_deployment` 使用）
   → 环境变量默认值。原有 `.env` 配置继续有效，作为兜底而非主路径。
6. **可用性判定收敛为一个异步入口** `accounts.is_available(adapter)`：注册表已有适配器，或存在
   启用的账号，即为可用。替换 `create_model`、部署写入路径与 `resolve_model` 里现有的同步
   `is_configured()` 判断，消除三处规则不一致。
7. **变更即时生效，不依赖广播。** 账号每次变更递增 `version`；连接池缓存键加入
   `(account_id, version)`；请求路径按部署查询顺带读取账号行。数据库即唯一真相来源，所有 worker
   立即收敛；内存后端本就是单进程。
8. **客户端按租约释放。** 请求持有一个租约，过期版本的客户端在最后一个租约释放后关闭。
   变更时立即 `aclose()` 会中断在途流式请求，不可接受。每个账号最多保留两个旧客户端以限制内存。
9. **凭证仍只存环境变量名。** 接口只返回值名与 `credential_present`，不返回值；审计快照不含密钥。
   UI 直接录入密钥属于 G2.4，需信封加密、KMS/主密钥、masked 读取、轮换与备份加密，作为后续阶段。
10. **管理面与审计沿用现有模式**：读接口任意管理员，写接口要求 `require_write_access`；
    动作名为 `provider_account.created|updated|deleted`，`target_type=provider_account`；
    被模型或部署引用时删除返回 409。控制台提供账号的列表、创建、编辑、启停、删除与探测结果展示；
    模型与部署表单改为选择账号，旧字段收进“高级”折叠区，避免两套入口并存。
11. **迁移 `0020`** 建表，并按 `model_deployments` 中不同的
    `(provider, credential_env, base_url)` 组合回填账号，随后把部署指向账号并清空旧列。
    仅回填至少设置了一个旧字段的部署；两个字段都为空的部署仍走环境变量默认值，不回填（它们没有
    可引用的行，也没有运维可见的身份）。旧列保留一个版本，明确弃用窗口后再删除。
12. **可选连通性探测**：由适配器声明廉价检查（OpenAI 兼容与 Anthropic 用 `GET /models`），
    短超时、不计用量、不回显密钥；没有廉价探测方式的适配器（Azure 数据面）明确返回“不支持”，
    而不是臆造请求。

## 备选方案

- **保留 `.env`，只做只读展示**：解决“看不见”，不解决“改一次要重启”，放弃。
- **把适配器导入路径存进数据库做动态加载**：等于在数据库里存可执行代码，安全边界失控，且新协议
  该写的转换代码一行不少，放弃。
- **密钥明文入库**：违反 §6，备份与审计都会扩散暴露面，放弃；加密入库属 G2.4。
- **把账号合并进部署表，不建新表**：仍无法在多条部署间复用同一账号，也解释不了模型级默认上游，
  放弃。
- **引入完整插件框架（entry points、钩子总线）**：当前只有 5 个适配器，收益不足以承担版本化契约
  与故障隔离成本，推迟到确有第三方扩展需求时。

## 后果

正面：

- provider 的增删改查进入界面与审计，新增 OpenAI 兼容上游不再需要重启。
- “一个适配器多个账号”成为一等概念，部署不再重复端点与凭证变量名。
- provider 可用性判定只有一套规则；Azure `api-version` 可以按账号配置，补上现在的全局限制。
- 密钥模型不变，安全评审面收敛在“只有变量名”这一点上。

负面：

- 请求路径多一次账号读取（可与部署查询合并）；连接池新增版本键与租约管理。
- 模型表与部署表出现可空外键与一段弃用期的冗余列。
- 回填迁移需要真实 PostgreSQL 验证，且回填后旧列清空属于一次性不可逆变更。
- 账号 `enabled=false` 与部署 `enabled=false` 是两级开关，UI 必须表达清楚，否则排障困难。

## 未决问题

- `usage_records` 与审计元数据是否记录 `account_id`，还是部署名已足够回答“哪个上游服务的”。
- 探测是否按账号限流，以及是否允许关闭。
- 旧 `credential_env`/`base_url` 列在哪个版本移除。
- 按租户 BYOK 与账号模型如何共存（属 G2.4）。
